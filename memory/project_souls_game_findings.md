From launching the built game and reading engine/game source (2026-08-30):

**Critical engine bug:** `AGT_TEMPLATE/engine/src/engine/core/application.cpp` `application::run()` computes `timestep` from raw unclamped frame time (`gameLoopTimer.elapsed()`), no max-dt clamp or fixed timestep/accumulator. Confirmed in practice: after the window lost real OS focus for a few seconds (during automated testing), the next frame's huge dt caused the player to go from full HP to 0 near-instantly against the boss — classic spiral-of-death / simulation-instability bug. This affects physics, combat timing, and anything frame-rate or stall dependent. High priority fix: clamp dt (e.g. cap at ~1/15s) or move to a fixed-timestep accumulator.

**Rendering is dated for a portfolio piece:** `game/assets/shaders/mesh.glsl` is labelled "PBR" in a comment but is actually classic ambient/diffuse/specular Blinn-Phong (struct `Material{ambient,diffuse,specular,shininess}`), max 2 point lights + 2 spot lights + 1 directional light, has fog support. No shadow mapping, no post-processing pipeline (no bloom/tonemapping/SSAO/framebuffer effects found anywhere in `engine/src/engine/renderer`). This is the single highest-leverage area for making the game look "industry standard" in screenshots/video.

**Architecture:** `game/src/example_layer.cpp` is a 1100+ line god-class doing scene setup, spawning, HUD text, input, and game-state (MainMenu/InGame/PauseMenu) all in one file/class. Player/Enemy/Boss/Priest each have their own small FSM-based logic classes (~150-300 lines) which is a reasonable pattern already — the fix is extracting scene/spawn/HUD/menu responsibilities out of example_layer rather than rewriting combat logic.

**Gameplay/level design observed:** game currently drops the player into a boss fight ("BOSS: DEVIL") essentially immediately with no explored intro/level pacing before it; environment had a giant grass card clipping right through the camera view (grass billboard/quad scale or placement bug); HUD is plain coloured debug-style text (`HP:`, `Stamina:`, `Potions:`, `Soul Fragments:`) with an ASCII bracket boss health bar — functional but not stylized. Main menu is plain black background with yellow/white text list, no visual polish, no video/logo.

**Repo hygiene is already fine:** build outputs (`bin/`, `inter/`) are correctly gitignored (`AGT_TEMPLATE/.gitignore`), not committed. No action needed there.

**Improvement roadmap discussed, by category:**
1. Engineering: fix dt clamping (critical correctness bug), break up example_layer god-class, consider ECS-lite or at least a SceneManager/UIManager/SpawnManager split.
2. Graphics: shadow mapping (single directional shadow map first), post-processing framebuffer pass (bloom + tonemapping at minimum), more dynamic lights, fix grass clipping, improve material setup (normal maps if assets allow).
3. Gameplay/level design: add pacing before the boss (exploration, weaker enemies first, checkpoints), death/game-over screen and respawn flow (currently unclear if one exists — HP hit 0 with no observed death UI), lock-on targeting (common souls-like expectation), i-frames tuning on roll.
4. Polish/UX: restyle HUD (health/stamina bars instead of raw numbers), stylized main menu, screen-space damage/hit feedback, sound feedback confirmation.

**How to apply:** when resuming this work, check with the user which category to tackle first rather than assuming — this was presented as a menu of options, not a committed plan. See [[project-souls-game-overview]] for how to build/run.

**Round 3 (2026-08-30):** User confirmed FOV kick is good. Reported two things:
1. "Return to Main Menu" (from pause or defeat) just replayed the game instead of showing the menu. Root cause: `example_layer::on_event` had multiple `if (m_game_state == X) {...}` blocks checked sequentially against the *live* (mutating) `m_game_state` within a single key event - selecting "Return to Main Menu" set state to MainMenu mid-handler, and the SAME Space keypress then fell through into the later `if (m_game_state == MainMenu)` block, whose `if (m_menu_selection == 0) { state = InGame }` fired immediately, bouncing straight back into gameplay. Fixed by snapshotting `const GameState state_at_event = m_game_state;` at the top of the key-pressed handler and gating every block on that snapshot instead of the live value - a general fix, not just a patch for this one path.
2. Roll "just does a falling-over/diving animation, not a real Elden-Ring-style roll." Since this can't be diagnosed without seeing the clip, added a one-time startup diagnostic in `player::initialise()` that logs every animation clip's index/name/duration for the player model via `LOG_CORE_INFO` (visible in the game's console window - `game.vcxproj` is `SubSystem=Console`) - waiting on the user to report what clips actually exist so we can pick a real roll if one's in the FBX, or accept `m_anim_dash` is the only option and reconsider `attack()`/`roll()` approach.

Also implemented this round - a combat readability request: **attack hit-arc VFX**. The player's melee hit-detection (`SpawnManager::update`, `Boss::check_hit_player` etc.) checks distance + facing-cone every frame while attacking, but the swing animation doesn't visually match that hit region, so hits feel arbitrary. In `example_layer::on_render`, while `m_player.is_attacking()`, a ~40°-wide band is rotated to sweep through a ~110° arc (roughly matching the dot>0.5 facing check) over the attack's duration (new `player::get_attack_progress()`, backed by a new `m_attack_duration` member set in `attack()`), rendered with the "mesh" shader in unlit/holographic mode (`lighting_on=false`), fading in and out via `sin(pi*progress)` envelope on the material's transparency. **Round 8 (2026-08-30) - second screenshot, two more concrete diagnoses:** the 36-degree/0.3-1.6-radius fix from round 7 rendered as two solid triangular wedges sitting apart with a gap between them (not crossing, not blade-like). Two causes:
1. `inner_radius=0.3, outer_radius=1.6` is a huge radial range relative to the arc - a ring segment with inner radius near zero and a large outer radius is geometrically a filled fan/wedge tapering to a point, not a uniform-thickness curved blade. Fixed by bringing inner/outer close together (`1.1f, 1.5f` - a thin 0.4-unit-wide band) so it reads as a curved sliver instead of a solid triangle.
2. 36 degrees was too narrow to overlap after the +/-45 degree stroke rotation - the two arcs' angular ranges (27-63 and -63-27) don't touch, leaving a visible gap (hence "two separate fins" instead of a crossing X). Widened to 100 degrees so the rotated strokes' ranges overlap near the centre.
Also implemented explicit request: strokes now play **sequentially**, not simultaneously - right slice ("\", `stroke_angles_degrees[0]=-45`) fades in/out during attack progress 0.0-0.5, left slice ("/", `+45`) during 0.5-1.0, each with its own `sin(pi*local_progress)` envelope confined to its half. Total visible duration still spans the full attack/hit-window duration, just as two consecutive halves now instead of one overlapped whole.
Build verified clean, first attempt, zero new warnings. Not yet visually re-confirmed.

**Round 14 (2026-08-30) - found the actual persistent root cause: the composite was hard-clamping an HDR scene.** User tested round 13 via F3 and sent a screenshot showing a completely different, worse failure than rounds 11-12: the whole 3D scene (trees, grass, castle, player - not just combat VFX) rendered as flat black silhouettes against blown-out white sky/ground, with sharp red/cyan fringing at every edge. Traced this to something present since round 10 that every previous round had misdiagnosed as a threshold/extraction problem: `bloom_composite.glsl` did `o_color = clamp(scene_colour + bloom_colour * u_bloom_intensity, 0.0, 1.0)` - a **hard** clamp. This scene's lighting is genuinely HDR (tree point lights alone use `DiffuseIntensity=25`, several overlapping), so large areas of `scene_colour` already sit well past 1.0 in the RGBA16F scene framebuffer before any bloom is even added. A hard clamp turns every one of those areas into identical flat white the instant any channel crosses 1.0, and because each RGB channel crosses that line at a slightly different point (different surfaces/lights contribute unevenly per channel), the boundary between "clipped" and "not yet clipped" reads as colour fringing - worse the more total brightness there is to clip, which is exactly why raising `u_bloom_intensity` from 0.25 (round 12) to 0.6 (round 13) suddenly pushed far more of the frame across that line at once and made a moderate, localized problem into a scene-wide one. Any pixel that was already in normal range (<=0.8) is completely unaffected (preserves the existing "don't tonemap/shift the whole game's look" intent), and only the genuinely-overbright excess (intense lights, and now bloom on top of them) gets a continuous, gentle roll-off instead of a razor edge - which is what should eliminate both the flat-white blowout and the per-channel fringing at its boundary. New files:
- `game/src/LevelEditor.h/.cpp` - the whole tool. **Shadow mapping (new):** a single directional-light shadow map, following the player rather than covering the whole 100-unit terrain (a fixed frustum that size would only give blocky, low-resolution shadows right where the player's looking - most single-shadow-map implementations make this same "follows the camera" tradeoff).
- `engine::shadow_map` (`engine/src/engine/renderer/shadow_map.h/.cpp`, new) - a depth-only FBO wrapper: one samplable depth texture, `GL_CLAMP_TO_BORDER` with a white (max-depth) border colour so sampling outside the frustum reads as unshadowed rather than producing a hard edge, `glDrawBuffer(GL_NONE)`/`glReadBuffer(GL_NONE)` since there's no colour attachment at all. Deliberately a separate class from `engine::framebuffer` rather than a new mode on it - a shadow map's "no colour, depth as a sampled texture" shape is different enough from framebuffer's "always has colour, optional depth renderbuffer" assumption that folding them together would mean threading a special case through code that doesn't need it.
- `render_command::clear_depth()` (new, mirrors the existing `clear()`/`enable_depth_test()` pattern) - clears just the depth buffer, since a depth-only target has no colour buffer to clear.
- `game/assets/shaders/shadow_depth.glsl` (new) - vertex stage is a trimmed copy of `mesh.glsl`'s own vertex shader (same attribute layout, same bone-skinning logic) so animated casters (player/enemies/boss/priest) cast a shadow in their actual current pose rather than a bind pose; fragment stage is empty (`void main(){}`) since only depth matters and there's no colour attachment to write to anyway.
- `mesh.glsl` changes: vertex stage gained `u_light_view_projection` uniform and outputs `v_light_space_pos` (computed the same way as `v_position` but through the light's matrix instead of the camera's) from both the skinned and non-skinned branches. Fragment stage gained `shadow_map`/`shadows_on` uniforms, a `calculate_shadow(normal)` function (3x3 PCF - percentage-closer filtering - to soften the shadow edge instead of one hard sample per fragment, plus a slope-scaled bias against shadow acne), and `CalcLightInternal` now takes a `ShadowFactor` param that dims the diffuse+specular contribution only (never ambient, so shadowed ground still reads as dimly lit rather than pure black) - only `CalcDirectionalLight` computes a real shadow factor; `CalcPointLight`/`CalcSpotLight` pass `0.0` (the single shadow map is only tested against the directional light).
- `ShadowRenderer` (`game/src/ShadowRenderer.h/.cpp`, new) - the game-side orchestrator: `render(light_direction, focus_position, draw_casters_callback)` computes the light-space matrix (ortho frustum, ~45-unit half-size, centred on the player, sourced from `m_directionalLight.Direction`) and renders whatever the callback submits into the shadow map; `bind_for_sampling(mesh_shader, texture_slot)` binds the result to texture unit 1 (unit 0 stays free for each object's own diffuse texture, matching the existing convention of textures always binding to unit 0) and sets `u_light_view_projection`/`shadows_on` on the main mesh shader. Same callback-based decoupling pattern as the now-removed `BloomEffect` used for its glow source.
- `example_layer::render_shadow_casters(shader)` (new) - submits every shadow-casting object (terrain, trees, rocks, primitives, halberd, `SpawnManager::render` for enemies/priests, boss, player) with whichever shader is passed in; skips the skybox (not a caster), grass (1500 cheap billboards - shadowing them would be visually noisy and costly for little benefit), and soul pickups/combat VFX (small/transient). Called once for the shadow pass (with `shadow_depth`) - not reused for the main pass, which still goes through the existing `render_static_world`/enemy/boss/player render calls with the `mesh` shader.
